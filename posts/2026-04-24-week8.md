## Refining the Audience: Why K-pop?

After establishing the functional requirements in Week 7, I spent this week narrowing down the specific community for my A2 prototype. I have decided to focus on **K-pop fandoms**. 

K-pop communities are unique because they are highly organized and driven by "contribution culture"—fans don't just consume content; they actively participate in "streaming parties," voting, and offline events to support their idols. However, this intensity often leads to toxic "gatekeeping" or the rise of bots that manipulate engagement metrics. By focusing on this niche, my **Fan Qualification System** transforms from a generic scoring tool into a **"Fandom Passport"**—a digital identity that verifies authentic, multi-dimensional support.

## From Requirements to Technical Logic (LO2)

The biggest challenge this week was deciding how to translate my abstract "qualification logic" into a functional web interface using the **Bla+Bla framework**. 

### 1. Server-Side State and HTMX for Real-time Feedback
To meet the requirement of showing "real-time qualification results" without full-page reloads, I plan to leverage **HTMX asynchronous requests** combined with **MojoJS controller actions** instead of heavy client-side state management. 

When a user clicks a "Simulate Stream" or "Attend Virtual Event" button, an `hx-post` request is triggered.
* **Decision:** I chose to use server-rendered HTML fragments (partials) to update the user's "Contribution Points" and "Passport Levels" dynamically.
* **Reasoning:** This allows the server to act as the single source of truth. The backend processes the action, updates the database, and immediately returns a reactive HTML partial (like an updated progress bar). This provides the instant feedback loop crucial for user retention in gamified environments while keeping the frontend lightweight.

### 2. Implementing Constraints (Anti-Abuse)
One of my core functional requirements was an anti-abuse system to prevent botting. Technically, this means implementing **conditional routing logic** within my MojoJS controllers to intercept requests before updating the database. 

For example, the backend controller function handles the engagement limit like this:

export async function handleEngagement(ctx: MojoContext): Promise<void> {
