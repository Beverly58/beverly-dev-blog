## Refining the Entity Relationship Diagram (LO1)

This week focused on refining the Entity Relationship Diagram (ERD) for the Fandom Passport system.

After creating the initial DDD last week, I reviewed the relationships between entities and identified several areas where the structure could be improved.

The system currently contains five core entities:
- Users
- Stamps
- Tasks
- User_Stamps
- Passport

Instead of treating the passport as a purely visual interface, I started considering it as a dynamic system generated through database relationships.

This helped me better understand how user progress, rewards, and achievements should function together.

---

## Improving Relationship Logic (LO2)

One major refinement this week was removing unnecessary duplicated data.

For example, I originally included a “total_stamps” attribute inside the User entity. However, after reviewing normalization principles, I realised this value can already be calculated through the User_Stamps table.

This means the system does not need to repeatedly store the same information.

### Updated Relationship Thinking

- One User can collect many Stamps
- One Stamp can belong to many Users
- Tasks reward specific Stamps
- Passport stores user progression and display information

The User_Stamps junction entity became increasingly important because it connects user activity with collectible rewards.

I also began thinking about how these relationships could support future interaction features such as:
- limited edition event stamps
- progression-based VIP levels
- redeemable rewards
- personalised passport pages

---

## Connecting Backend Structure with Future Interaction Design (LO3)

This week made me realise that backend planning directly affects interaction possibilities.

For example:
- a repeatable task system allows users to continuously earn points
- redeemable stamps create opportunities for reward exchange
- dynamic passport slots support personalised layouts
- timestamp data allows activity history tracking

These features are not only technical considerations but also interaction design decisions.

I also started considering scalability more seriously. If new fandom events or campaigns are introduced in the future, the system should be able to support additional stamps and tasks without redesigning the entire structure.

This aligns with the DRY principle discussed in lectures, where reusable systems reduce redundancy and improve maintainability.

## Reflection

Compared to previous weeks, this stage felt much closer to actual product system design rather than only visual interface design.

The ERD process helped me understand that good interaction design is deeply connected to information structure and database relationships.

It also changed how I think about “features.” Many interface elements that seem simple visually actually require complex backend relationships to function properly.
